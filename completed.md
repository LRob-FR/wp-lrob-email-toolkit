# Shipped — version history

Concise, fact-checked record of what's actually in the codebase. Each version lists user-facing features + load-bearing technical decisions. Implementation details live in the code; this file is "what does the plugin do today and when did each capability arrive".

For the **backlog** (what's not done yet), see [todo.md](./todo.md).
For working rules (conventions, naming, build, UI patterns), see [CLAUDE.md](./CLAUDE.md).

---

## v0.3.x — Newsletter module (alpha → being hardened)

### v0.3.4
- **Gender form field type.** New `gender` field type for newsletter subscribe forms (`Modules/Newsletter/Fields/GenderField`). Self-contained: renders a `<select>` with options auto-populated from `SubscriberFields::GENDER_VALUES` (female / male / other / prefer_not_to_say), labels translated via `gender_label()` at render time so a locale switch flips them without admin re-save. Locks `maps_to=gender` so it always feeds the right column. Replaces the previous `select` + `maps_to=gender` preset (dropped from `FormsPage::field_presets()`) and the manual-select setup in the *Full profile* form template. Surfaces in the field-type picker as "Gender" alongside Text / Email / Phone. Composite address field type still deferred — the *Postal address* preset already covers the functional need (5 mapped text fields in one click).
- **Subscriber self-edit + email-change confirm flow (Schema v14).** Subscribers can now edit their profile + change their email from the public prefs page (`?lrob-etk-nl-prefs=<token>`), the prefs block on any public page, and the WP profile section (WP users skip the profile-edit section — they have their own WP profile screen). **Profile self-edit**: new fieldset "Your details" listing first/last name, phone, gender (select), full postal address. Saves via `profile[<column>]=<value>` POST shape; PrefsHandler whitelists against `SubscriberFields::PROFILE_COLUMNS` server-side. Email column explicitly skipped here — it has its own confirm-on-new-address flow. **Email-change confirm flow**: new schema v14 columns on `subscribers` — `pending_email`, `pending_email_token` (indexed), `pending_email_requested_at`. New repository methods `set_pending_email_change` / `find_by_pending_email_token` / `confirm_pending_email_change` / `cancel_pending_email_change`. **Dispatcher**: new `EmailChangeDispatcher` sends two emails on request — a confirm message to the NEW address (carrying the click-to-confirm URL embedding the single-use token, 24h TTL), plus a notice message to the OLD address ("Someone asked to move your subscription to X — nothing happens until they confirm"). Hardcoded HTML wording (load-bearing for trust, not a CPT template). **Handler**: new query param `?lrob-etk-nl-confirm-email=<token>` resolves the token, applies the change, renders a self-contained status page. Outcomes mapped: `ok` / `expired` (24h) / `email_taken` (race) / `invalid`. Cancel-pending button drops the staged state without confirmation. **WP user prefs**: simple master "Receive newsletter emails" toggle kept as-is, with a description clarifying that transactional emails (password resets, order notifications) keep coming regardless — to stop those, delete the WP account. (GDPR self-serve account-deletion flow deferred to the future GDPR toolkit.) New event `newsletter.subscriber.email_change_requested`.
- **Newsletter form-template presets — Contact basics + Full profile.** `FormTemplateRegistry` extended with two new starters that lean on the v0.3.4 profile fields: **Contact basics** (first name + last name + email + phone) and **Full profile** (every profile field: name halves, email, phone, gender select, postal address with country dropdown). They surface automatically in the existing "Start a new subscribe form" picker — admins land on a curated form instead of building from blank. Newsletter form CPT now registers `PhoneField` + `SelectField` (previously only email/text/submit + captcha/list-picker) so the new presets render correctly on the frontend AND surface in the generic-field picker ("Phone", "Dropdown (select)"). Country options come from the shared `CountryData::all_translated('name')` so the picker mirrors the international phone field's catalogue + the address column stays a clean ISO-2.
- **Audience dropdown polish — System / provider badges, system-last ordering, full-name summary, real users-kind counts.** Each audience-menu row now carries the same badges as the Lists modal: `lrob-etk-nl-list-system-badge` for built-ins, `lrob-etk-nl-list-provider-badge` for rule-driven users-kind lists (label from the registered provider). Within each kind section (Subscribers / WP users), system rows are pushed to the end so the user's own lists land at the top. **Real counts everywhere**: `ListRepository::member_counts()` now resolves rule-based lists too (union of manual `list_members` rows + `resolve_rule_user_ids`, deduped). Counts are 5-minute transient-cached (`lrob_etk_nl_list_counts`); every mutator (`insert` / `update_rule` / `delete` / `add_member` / `remove_member` / `detach_recipient`) busts the cache. Users-kind list members are no longer shown as `—` — they show the real total including rule matches. **Full-list summary**: the audience trigger drops the `+N other(s)` abbreviation; picked lists are now comma-joined in full. CSS `text-overflow: ellipsis` handles overflow gracefully when many lists are selected.
- **Audience picker — dropdown of grouped checkboxes + live recipient count + default-none.** Replaces the chips+`<select>` adder from earlier in v0.3.4. The newsletter card now renders one **Recipients** field (Audience + Recipients merged into a single block) carrying a trigger button: bold count + summary of picked lists, click opens a dropdown menu of grouped checkbox rows (**Subscribers lists** / **WP users lists** sections matching the Lists modal order + style). Each row shows the list name + member-count pill (exact for subscribers-kind, manual-only for users-kind). Toggling a checkbox autosaves immediately, fires the `lrob-etk-nl-saved` event that `newsletter-cards.js` listens for, and the recipient count refreshes via the existing `recipients-preview` AJAX endpoint — no more reload-to-see-the-new-count. Menu closes on outside-click or Escape. **Default-none**: brand-new newsletters (no `META_TARGET_SPEC` yet) and any newsletter saved with zero picked lists now resolve to **zero recipients** instead of falling back to "everyone". The previous default-everyone footgun let an admin click Send before realising they hadn't picked an audience; now the trigger reads *"no list picked — pick one to send"* in italics until a list is checked. **Email-level dedup**: `Materializer::dedupe_by_email` ensures a recipient who exists as both a subscriber row AND a WP user (same email) gets the newsletter once — WP user wins (stable identity, login, prefs token). **Manage-lists trigger restyle**: dropped the chunky icon-button for a plain `lrob-etk-nl-field-link` text link (`Manage lists →`) matching `Manage identities →`. **"All subscribers" placement**: the pseudo-system list now displays under the **Subscribers lists** section in both the Lists modal AND the audience dropdown (was orphaned as a third group). **`AUDIENCE_KEYS` bug fix**: `newsletter-cards.js` was only listening for `target_kind` / `target_list_id` saves, so the new `target_list_ids` multi-list save never triggered a count refresh — added it to the array.
- **Categories → Lists merge (Schema v12 + v13).** The "category" concept retired in two passes:
  - **v12 (data migration)**: every former category becomes a public Subscribers-kind list with the same name + slug; subscribers who hadn't opted out of a category get an explicit `list_members` row in the new list. WP users with explicit `lrob_etk_nl_opted_in=1` are materialised the same way. Newsletters whose `META_CATEGORY_ID` was set get their `META_TARGET_SPEC` rewritten to `{kind:'lists', list_ids:[<new_id>]}` — but only when the existing target was `all` / `all_users` / `all_subscribers` (multi-list targets already configured aren't clobbered). Idempotent migration guarded by `lrob_etk_nl_categories_merged_into_lists` option; re-runs are safe (INSERT IGNORE on UNIQUE keys + slug-existence check).
  - **v13 (destructive cleanup)**: drops the `wp_lrob_etk_nl_categories` table, the `subscribers.category_opt_outs` column, and every `lrob_etk_nl_category_opt_outs` user_meta row in one upgrade pass. v12 + v13 chained on the same upgrade so users coming from v11 catch both. Each step guarded against re-run (information_schema check on the column, IF EXISTS on the table).
  - **New schema column `lists.visibility`** ('private' | 'public') — private = admin-managed (default), public = surfaced on the subscriber preferences page so subscribers can self-join/leave. System lists hardcoded private.
  - **PrefsRenderer rework**: subscribers see one section (Mailing lists) where each row is a public-list membership toggle; no more category checkboxes. Server enforces the public-only set on save — even if a subscriber tampers with the POST, only `visibility=public + kind=subscribers + is_system=0` lists are accepted.
  - **Materializer cleanup**: drops the `category_opt_outs` JSON filter — recipient resolution is now purely list-membership-driven.
  - **Admin UI**: Categories sub-page + "Manage categories" tools button + Newsletter card's Category picker all gone. Lists modal grows a per-row visibility chip (Private ↔ Public toggle) on non-system subscribers-kind lists + a member-count badge per row (exact for subscribers-kind, manual-only for users-kind — rule matches materialise at send time). The "All subscribers" pseudo-system list now displays under the Subscribers section (was orphaned as a third group, breaking the modal on every render). The Newsletter card's "Manage lists" trigger drops the chunky button styling for a `lrob-etk-nl-field-link` text link matching "Manage identities →".
  - **Dropped classes**: `CategoryRepository`, `CategoryPicker` field type, `Schema::TABLE_CATEGORIES` + `categories_table()`, `UserMeta::CATEGORY_OPT_OUTS`, `SubscriberRepository::set_category_opt_outs`, `seed_default_category()`, `category_picker` from `FormsPage::field_types`, the back-compat slug-lookup shim in `SubmitHandler::extract_chosen_lists`, the `UserHooks::promote_subscriber_to_user` line that copied `category_opt_outs` into user_meta. AJAX endpoints `ACTION_CATEGORY_{CREATE,RENAME,DELETE}` + `ACTION_LIST_VISIBILITY_SET` swap (3 dropped, 1 added).
- **Audience picker — multi-list with chips.** Newsletter card's audience field drops the kind-radio cluster entirely. New chip-list picker: each picked list shows as a chip with × to remove; a "+ Add a list…" dropdown lists every available list (system + user) with already-picked options disabled. Schema: META_TARGET_SPEC grows `{kind:'lists', list_ids:[…]}`; Materializer iterates list_ids and unions resolved recipients per `list.kind`, deduping by (kind,id). New AJAX pseudo-key `target_list_ids` (comma-separated, server-validates each ID against the lists table, drops unknowns). Legacy `target_kind=all` / `all_users` / `all_subscribers` / single `list` shapes keep working under the hood — only the UI changes. Newsletter card grows a **Manage lists** button next to the Audience label that opens the lists modal directly (reuses the existing `lrob-etk-nl-lists-btn` opener).
- **System (built-in) lists — All subscribers / All WP members / All WC customers / Active WC subscribers.** Schema v11 adds `lists.is_system` flag; install + migrate seed four built-in users-kind / pseudo-kind lists. Slugs reserved: `all_subscribers` (new pseudo-kind that Materializer resolves to every confirmed subscriber — no membership table needed), `all_wp_members` (WpAllUsersRule), `all_wc_customers` (new `WcCustomersRule` matching `customer`-role users via get_users; inert when WC absent), `active_wc_subs` (`WooSubscriptionsRule` locked to `statuses=['active']`). System lists show a *System* badge, hide the trash icon + Set rules + rename (input is readonly), but **keep Manage exclusions** so admins can pin specific WP users out of the audience. `ListRepository::delete` / `handle_list_rename` / `handle_list_rule_save` all refuse to act on `is_system=1` rows. Reusable from the Newsletter audience picker via the same dropdown.
- **List kinds + provider locked at creation.** New `lists.kind` column ('subscribers' / 'users') — Subscribers list = explicit memberships only (the legacy model); WP users list = rule-based, provider locked at creation time and never swappable post-hoc. Schema v10 migration: existing lists with rule_json become kind='users', everything else stays 'subscribers'. The list-create dropdown carries kind+provider in one shot (no later "Mode" picker — `kind` and `mode` were redundant). Materializer branches on the list's kind so subscribers / users sides stay semantically distinct. WC Subscriptions provider gains a proper `wc_product_search` field type — AJAX search backed by `wc_get_products`, multi-chip picker via `ACTION_WC_PRODUCT_SEARCH`; replaces the comma-separated product IDs hack. The picker idiom is reusable for the future WC-orders rule. Per-rule exclusions live in `wp_lrob_etk_nl_list_exclusions(list_id, user_id, reason)`; admin search-pick WP users via `ACTION_WP_USER_SEARCH` + chips, Materializer subtracts the exclusion set from resolved IDs.

Row layout uses `flex: 1 1 auto; min-width: 0` on the name so the trash icon stays right-anchored even on long names that wrap. Trash button is now an `icon-btn--danger`, Set rules + Manage exclusions are icon-btns inside the row-actions span (right side). The rule editor drops the in-row Mode dropdown (provider is locked); drops the explicit Save button — config field changes **autosave** debounced 350ms per the `autosave-everywhere` rule. Drops the inline "✓ Saved — matches N user(s)" status text that was shifting the layout below; the modal-header save badge carries the feedback now. Manage exclusions moves from a row-actions icon into a button inside the rule-editor panel (where it logically lives), with the picker rebuilt around a WP-user search instead of the paste-emails textarea (`ACTION_WP_USER_SEARCH`).

Bulk ops: Trash / Restore from trash / Delete permanently — via new `ACTION_SUBSCRIBERS_BULK`, confirm prompt via the shared in-modal helper. Per-row checkbox in a `col-bulk-check` first column. New per-admin column visibility picker (header tool button with the `dashicons-editor-table` glyph, opens a modal): 15 columns available (`email`, `name`, `first_name`, `last_name`, `phone`, `gender`, `language`, `status`, `created_at`, `source`, `lists`, `opens`, `clicks`, `sends`, `confirmed_at`). - **Subscribers import — all profile fields.** Paste + CSV upload modal extends to honour every PROFILE_COLUMN. CSV header auto-detect (any column slug matching the registry: email, name, first_name, last_name, phone, gender, language, address_*); paste mode keeps the simpler `email` / `email, name` shape. Security: every key on every row passes through `SubscriberFields::sanitize` server-side (whitelisted against PROFILE_COLUMNS — sanitize_email for email, ENUM check for gender, ISO-2 cap for country, sanitize_text_field for the rest). Header text on the modal documents the supported columns.
- **Plugin-wide save-status mechanic + modal autosave plumbing.** New shared `etk-confirm.js` companion: `etk-modal.js` injects a `[data-modal-status]` badge in every modal header on first interaction, listening for a bubbling `lrob-etk:save-status` CustomEvent (states `saving` / `saved` / `error`). Every autosave path dispatches the event — `etk-autosave.js` (CF + Logs), `newsletter-admin.js` (per-key list/category renames + newsletter card meta), and the rule-editor autosave path. Result: every modal in the plugin shows "Saving… / ✓ Saved / ✗ Error" near its close button without each consumer having to discover/style its own badge. Plugin-wide rule (memory `feedback_autosave_everywhere`): no explicit Save buttons in admin UIs — every editable field autosaves, badge in the modal header.
- **Form-editor presets + uniform page header + tickbox-style multiselect.** **Page header**: `.lrob-etk-page-header` now carries a 1px bottom border + 14px padding so every page surfaces the same divider line — SMTP, Captcha and the rest stop drifting visually from Dashboard / Contact Forms. Captcha settings page drops its stray intro paragraph (header text + section titles already carry the meaning). **Tickbox multiselect**: the rule-editor `multiselect` field type renders as a checkbox-pill group instead of `<select multiple>` (the Ctrl-click idiom that confused everyone). Stale entries — e.g. roles whose plugins were since removed — survive the round trip: they render with a warning chip and the *(missing)* label so the admin sees what's about to be dropped. `WpUserRoleRule::sanitize_config` + `resolve_user_ids` both filter against the live `WP_Roles` registry, so a stale role never reaches the user query. **Form-builder presets**: Newsletter subscribe-form editor's "+" picker grows a "Quick add (pre-mapped)" section above the generic field types. Five built-in presets — *Full name*, *First + Last name*, *Phone*, *Gender* (radio with the inclusive M/F/Other/Prefer-not options), *Postal address* (5 fields: street / line2 / postcode / city / country) — each pre-fills the new field's label + `maps_to` attribute so submissions populate the right subscriber columns automatically. Presets expose `{ slug, label, fields: [...] }` via `EDITOR_DATA.fieldPresets`; on the JS side, `findPreset` + `buildPresetField` + `buildRowsForChoice` handle picker callbacks that may return either a single type or a multi-field preset. The preview endpoint accepts `limit` + `offset` so the UI grows a *Load more (N)* + *Show all* footer when total > shown, paginated 50 at a time.

- **Form-field "Maps to" subscriber-column picker.** Each form-builder field grows a "Maps to" inline-settings chip (Newsletter subscribe forms only — Contact Form passes the picker an empty `mapsToTargets` so the chip stays hidden). Editor JS serialises `maps_to` into the form structure JSON; `FieldRenderHelpers::normalize_base_keys` keeps it through the save round-trip; `FormEditorRenderer::render_field` emits `data-attr-maps_to` so re-opening a saved form rehydrates the picker. Subscribe submit handler grows two methods: `extract_mapped_profile` walks the form structure for every field carrying a `maps_to` ≠ `email` and returns `column => sanitised value`; `write_mapped_profile` fans the payload onto `set_profile_field`. Applied after both fresh inserts and resubscribe (`reset_to_pending`) paths. Means: an admin can build a subscribe form with separate First name / Last name / Phone / Address fields, map each to the right column, and the row gets fully populated — no field-name guessing.
